# Diamond High — Prototype Roadmap

This roadmap covers only the first demonstrable e-school prototype. It is separate from the [Long-term Product Roadmap](PRODUCT_ROADMAP.md). It is directional, not a fixed schedule; progress depends on learning, available time, and review.

## Stage 0 — Recovery and baseline refinement
- [ ] Inventory and inspect the repository and existing implementation.
- [ ] Reconcile historical school-website documents with the current e-school identity.
- [ ] Recover and confirm the product's audiences, learning journey, and candidate modules.
- [ ] Review the existing design reference and establish the new Lunacy workspace.
- [ ] Define the prototype's content, learner journey, and completion criteria.
- [ ] Review the technical and learning baseline.
- [ ] Obtain the user's approval of the consolidated baseline.

**Exit condition:** The e-school identity, first learner journey, prototype scope, design direction, and next milestone are clear and approved.

## Stage 1 — E-school landing page
- Clarify the landing page's communication goals and information architecture.
- Learn and apply layout composition, hierarchy, typography, spacing, colour, and responsive design.
- Design the landing page in Lunacy.
- Review the design at meaningful milestones.
- Implement only after the design and baseline are approved.
- Test navigation, responsiveness, accessibility, and key interactions.

**Exit condition:** The landing page clearly introduces Diamond High as an e-school and guides learners into the prototype experience.

## Stage 2 — One integrated learning journey
- Select one representative subject/course and learning objective.
- Design and build a structured lesson.
- Add a meaningful practice activity.
- Provide explanatory feedback and a reasonable retry/review path.
- Show a simple, honest progress state and next step.
- Test the journey end to end.

**Exit condition:** A reviewer can complete the learner journey and understand what the prototype demonstrates.

## Stage 3 — Review and refinement
- Gather feedback where possible.
- Separate observed feedback from assumptions and personal preferences.
- Evaluate whether the learning activity supports the intended objective.
- Prioritise improvements by learner value, effort, and risk.
- Document capabilities and limitations.

**Exit condition:** The next iteration is based on evidence and a clear review.

## Stage 4 — Engineering improvement
As justified by the product, improve reusable components, testing, accessibility, performance, maintainability, and deployment workflow. Choose specific technical tools only when requirements make the trade-offs clear.

## Working rhythm

For each milestone:
1. Agree on a small, observable goal.
2. Inspect the current project and relevant files.
3. Learn the theory needed for the design or engineering task.
4. Let the creator apply the concepts independently.
5. Review at meaningful checkpoints rather than through constant micro-checks.
6. Test behaviour and review the result.
7. Record consequential decisions and unresolved issues.
8. Move forward when the result is understood well enough to maintain.

Avoid inventing deadlines without considering the user's actual schedule and energy. Prefer steady, demonstrable progress over rushed volume.
